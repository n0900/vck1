# Known standards conflicts and decisions

This register records conflicts affecting the CSC and ETSI remote signing implementation. 

| Issue                                      | Requirement A                                                                                                               | Requirement B                                                                                                                                                                                        | Status                                                             | Decision                                                                                                                                                                                                                                                                                                                                              |
|--------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| mdoc `qesApproval` digest algorithm        | ETSI TS 119 432 V1.3.1, B.6.3 specifies that the hash algorithm is the request's `hashAlgorithmOID`.                        | CSC Data Model Bindings 1.0.0, 7.2.1.1 requires the mdoc `qesApproval` CBOR `bstr` to contain a SHA-256 digest.                                                                                      | **Approved.** Mediated by the user: follow TS 119 432.             | Use the supported algorithm identified by the request's `hashAlgorithmOID` for mdoc approvals, following ETSI B.6.3. This intentionally differs from CSC's fixed SHA-256 requirement and covers digest algorithm selection only. The previously approved hash-input rule remains in effect.                                                           |
| SD-JWT `qesApproval` hash input            | ETSI TS 119 432 V1.3.1, B.6.3 requires hashing the UTF-8 JSON bytes. <br/>`base64(hash(original UTF 8 qesApprovalRequest))` | CSC Data Model Bindings 1.0.0, 7.2.1.2 (SD-JWT VC-based encoding) requires hashing the base64url representation of the UTF-8 JSON. <br/>`base64(hash(base64Url(Original UTF 8 qesApprovalRequest)))` | **Approved.** Mediated by the user: retain the CSC format for now. | Retain CSC's format-specific behavior: SD-JWT hashes the UTF-8 bytes of the original base64url `transaction_data` text; mdoc hashes the original decoded UTF-8 JSON bytes. Preserve the received representation without reserializing JSON. This decision covers approval hash input only; the SD-JWT behavior intentionally differs from ETSI B.6.3. |
| Document reference checksum representation | ETSI TS 119 432 V1.3.1, A.6.4 specifies the structured Hash object from CSC Data Model 1.0.0, 7.4.                          | CSC Data Model Bindings 1.0.0 checksum requirements specify SRI syntax.                                                                                                                              | **Approved.** Previously mediated by the user.                     | Use structured Hash throughout the active project paths. Retain `ChecksumSerializer` as an unused object with `@Suppress("unused")` and explanatory KDoc. Do not add active SRI compatibility. This approval covers document reference checksum representation only.                                                                                  |
| X.509 capability metadata definition | OpenID4VP 1.0, 10.1 and 11.1 define `vp_formats_supported` entries as credential format identifiers mapped to format-specific capability parameters; additional formats require agreement between participants. | CSC Data Model Bindings 1.0.0, 8 defines `https://cloudsignatureconsortium.org/2025/x509`, its DCQL `x509MetadataQuery`, and its `x509PresentationResponse`, but no `vp_formats_supported` parameter object. ETSI TS 119 432 V1.3.1, A.3–A.6 does not supply that definition either. | **Pending.** Capability metadata definition missing from the local editions. | Defer X.509 capability advertisement until standards clarification or an explicitly mediated extension defines the entry. Do not invent algorithm fields or reuse DCQL certificate-selection constraints as capability parameters. Whether an empty object is sufficient also remains unresolved; this register does not authorize a guessed implementation. |

## Section for Agents
Requirements above refer to the local editions listed in the csc_2.2.0.0/.
Pending decisions do not authorize implementation of a proposed resolution. Approved decisions apply only
within their recorded scope; newly discovered conflicts require separate mediation.
